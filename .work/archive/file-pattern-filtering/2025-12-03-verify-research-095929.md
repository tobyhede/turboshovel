# Research Report: Minimatch Glob Pattern Validation in TypeScript

## Metadata
- Date: 2025-12-03
- Researcher: research-agent
- Scope: Best practices for validating glob patterns with minimatch at config load time in TypeScript/Node.js

## Research Questions
1. Does minimatch throw errors for invalid glob patterns like `packages/[abc/**`?
2. Does `makeRe()` provide better validation than `minimatch()`?
3. What do other TypeScript projects (Jest, ESLint, Webpack) do for glob validation?
4. Is fail-fast validation at config load time idiomatic, or should we defer to runtime?
5. Can the original implementation plan's approach work (try-catch around minimatch)?

## Key Findings

### Finding 1: minimatch() Does NOT Throw for Malformed Glob Patterns
- **Source:** Direct testing with minimatch@10.1.1 (current project version)
- **Evidence:**
  ```javascript
  minimatch('test.js', 'packages/[abc/**')  // Returns: false (no error)
  minimatch('test.js', 'packages/{a,b/**')  // Returns: false (no error)
  minimatch('test.js', 'packages/test[')    // Returns: false (no error)
  ```
- **Confidence:** HIGH (direct empirical testing)
- **Implication:** The plan's assumption that minimatch throws for syntax errors is incorrect. Try-catch will not catch malformed patterns.

### Finding 2: minimatch() ONLY Throws for Type Errors
- **Source:** Direct testing with minimatch@10.1.1
- **Evidence:**
  ```javascript
  minimatch('test.js', [])        // Throws: TypeError: invalid pattern
  minimatch('test.js', 123)       // Throws: TypeError: invalid pattern
  minimatch('test.js', null)      // Throws: TypeError: invalid pattern
  minimatch('test.js', undefined) // Throws: TypeError: invalid pattern
  ```
- **Confidence:** HIGH (direct empirical testing)
- **Implication:** Try-catch is useful for catching TypeScript type system bypasses (runtime type errors), but not for glob syntax validation.

### Finding 3: makeRe() Returns false for Invalid Patterns
- **Source:** [Minimatch GitHub README](https://github.com/isaacs/minimatch), direct testing
- **Evidence:**
  - Documentation: "Generate the regexp member if necessary, and return it. Will return `false` if the pattern is invalid."
  - Testing: Empty pattern `''` returns false from makeRe()
  - However: `packages/[abc/**` still produces a regex (doesn't return false)
- **Confidence:** MEDIUM (documented but behavior unclear for which patterns are "invalid")
- **Implication:** makeRe() returning false is for patterns that can't be compiled to regex, not syntax validation. Minimatch is lenient and tries to interpret patterns even with malformed brackets.

### Finding 4: Ecosystem Does NOT Validate at Config Load Time
- **Source:** [Jest Configuration Docs](https://jestjs.io/docs/configuration), [ESLint Configuration Docs](https://eslint.org/docs/latest/use/configure/configuration-files), [Webpack Glob Entry](https://www.npmjs.com/package/webpack-glob-entry)
- **Evidence:**
  - Jest: Uses micromatch, recommends "consult the micromatch documentation to ensure your globs are compatible" if patterns don't match
  - ESLint: Uses minimatch syntax, no validation mentioned in config docs
  - Webpack: Plugins like webpack-glob-entry expand globs at build time, no pre-validation
- **Confidence:** HIGH (official documentation reviewed)
- **Implication:** The idiomatic approach in the TypeScript/Node.js ecosystem is NOT to validate glob patterns at config load time. Runtime errors or "no matches" are the norm.

### Finding 5: Minimatch is Extremely Lenient
- **Source:** Direct testing with minimatch@10.1.1
- **Evidence:**
  - `packages/[abc/**` compiles to regex: `/^packages\/\[abc(?:\/|\/(?:(?!(?:\/|^)\.).)*?)?$/`
  - Unclosed brackets are treated literally (as `[` characters)
  - Unclosed braces are not expanded
  - This is intentional design - minimatch tries to interpret patterns
- **Confidence:** HIGH (direct testing, consistent with glob philosophy of permissive matching)
- **Implication:** There's no reliable way to detect "invalid" patterns because minimatch interprets almost anything as valid. What users think is invalid may just be a literal match.

### Finding 6: Config Load Validation Trade-offs
- **Source:** Research synthesis from ecosystem patterns
- **Evidence:** No major TypeScript tools validate glob patterns eagerly
- **Confidence:** HIGH (consistent pattern across multiple projects)
- **Implication:**
  - **Pro (fail-fast):** Catch typos early, better UX for config errors
  - **Con (runtime):** Simpler code, consistent with ecosystem, patterns work even if unusual
  - **Verdict:** Runtime validation is more idiomatic in JavaScript/TypeScript ecosystem

## Patterns Observed

1. **Ecosystem Pattern:** Tools that use globs defer to runtime - no config-time validation is standard
2. **Error Philosophy:** Glob libraries are permissive, not strict - they try to interpret patterns liberally
3. **TypeScript Integration:** Type safety (string type) is the primary validation, not syntax checking
4. **makeRe() Usage:** When used, it's for performance (pre-compile regex), not validation
5. **User Experience:** Documentation and clear error messages are preferred over strict validation

## Gaps and Uncertainties

1. **Minimatch v9 vs v10 behavior:** Testing was only on v10.1.1 (current version). Earlier versions may differ, but this is the relevant version for the project.

2. **What constitutes "invalid":** There's no formal spec for what makes a glob pattern invalid. Users may expect `packages/[abc/**` to be invalid, but minimatch treats it as valid (literal bracket).

3. **Alternative validation libraries:** Didn't research dedicated glob validation tools (if they exist). This might be a gap if strict validation is required.

4. **Edge cases with very long patterns:** Minimatch has a pattern length limit, but didn't test where this boundary is or how it's enforced.

5. **Brace expansion complexity:** The 2022 ReDoS vulnerability in brace expansion was mentioned but not deeply investigated. Modern versions should be safe, but performance characteristics with complex patterns remain uncertain.

## Summary

**The idiomatic TypeScript/Node.js approach is NOT to validate glob patterns at config load time.**

### What minimatch Actually Does:
- ✅ Throws `TypeError` for non-string inputs (type validation)
- ❌ Does NOT throw for malformed glob syntax
- ⚠️ Returns `false` from matches (not errors) for patterns that don't match
- ⚠️ `makeRe()` returns `false` only for patterns that can't compile (rare, like empty string)

### What the Ecosystem Does:
- Jest, ESLint, Webpack: No config-time glob validation
- Runtime behavior: Pattern doesn't match → no files found → documented as user error
- Philosophy: Permissive interpretation, defer errors to runtime

### Current Plan Status:
❌ **Original assumption is incorrect:** The plan states "minimatch would throw errors for invalid patterns" but testing shows minimatch does NOT throw for syntax errors.

✅ **Try-catch is still useful:** But only for type errors (non-string inputs), not syntax validation.

## Recommendations

### Recommendation 1: Keep Try-Catch for Type Safety Only (RECOMMENDED)

**What to do:**
```typescript
export function validateFilePatterns(gateConfig: GateConfig): void {
  if (!gateConfig.file_patterns || gateConfig.file_patterns.length === 0) {
    return;
  }

  for (const pattern of gateConfig.file_patterns) {
    // Type validation only - catches runtime type bypasses
    if (typeof pattern !== 'string') {
      throw new Error(`Invalid file pattern: expected string, got ${typeof pattern}`);
    }
    // No syntax validation - defer to runtime matching behavior
  }
}
```

**Rationale:**
- Consistent with ecosystem patterns (Jest, ESLint, Webpack)
- Simple, maintainable code
- Catches actual errors (type mismatches) without false positives
- Users discover pattern issues when they don't match files (natural feedback)

**Trade-offs:**
- ✅ Idiomatic, ecosystem-aligned
- ✅ No false positives from minimatch's lenient parsing
- ✅ Simple implementation
- ❌ Doesn't catch user typos at config load time
- ❌ Error appears at runtime (when gate doesn't run) not config load

**Original plan compatibility:** Requires removing the `minimatch('', pattern)` test call, keeping only the try-catch for non-string inputs.

### Recommendation 2: Use makeRe() for Pre-compilation (ALTERNATIVE)

**What to do:**
```typescript
export function validateFilePatterns(gateConfig: GateConfig): void {
  if (!gateConfig.file_patterns || gateConfig.file_patterns.length === 0) {
    return;
  }

  for (const pattern of gateConfig.file_patterns) {
    try {
      const mm = new Minimatch(pattern);
      const re = mm.makeRe();
      if (re === false) {
        throw new Error(`Pattern cannot be compiled to regex: "${pattern}"`);
      }
    } catch (error) {
      throw new Error(
        `Invalid file pattern "${pattern}": ${error instanceof Error ? error.message : String(error)}`
      );
    }
  }
}
```

**Rationale:**
- Catches the small subset of patterns that can't compile (empty strings, extreme edge cases)
- Validates type errors
- Slightly more validation than Recommendation 1

**Trade-offs:**
- ✅ Catches patterns that would fail at runtime
- ⚠️ Still doesn't catch "user typos" like `packages/[abc/**` (minimatch accepts these)
- ❌ More complex than ecosystem norm
- ❌ Minimal benefit over Recommendation 1

**Original plan compatibility:** Similar to current plan but uses `makeRe()` instead of calling `minimatch()`.

### Recommendation 3: Manual Syntax Checking (NOT RECOMMENDED)

**What to do:**
```typescript
function hasMalformedBrackets(pattern: string): boolean {
  let depth = 0;
  for (let i = 0; i < pattern.length; i++) {
    if (pattern[i] === '[' && pattern[i-1] !== '\\') depth++;
    if (pattern[i] === ']' && pattern[i-1] !== '\\') depth--;
    if (depth < 0) return true;
  }
  return depth !== 0;
}

export function validateFilePatterns(gateConfig: GateConfig): void {
  for (const pattern of gateConfig.file_patterns) {
    if (hasMalformedBrackets(pattern)) {
      throw new Error(`Malformed brackets in pattern: "${pattern}"`);
    }
    // Similar for braces...
  }
}
```

**Rationale:**
- Provides the strict fail-fast validation originally envisioned
- Catches user typos at config load time

**Trade-offs:**
- ❌ Not idiomatic - ecosystem doesn't do this
- ❌ Complex to implement correctly (brackets, braces, escaping, negation, ranges)
- ❌ Risk of false positives (rejecting patterns minimatch would accept)
- ❌ Maintenance burden (must update if glob spec changes)
- ❌ Fighting against minimatch's permissive design

**Original plan compatibility:** Could be added but contradicts ecosystem patterns.

## Final Recommendation

**Use Recommendation 1: Type validation only, no syntax validation.**

### Code Example

```typescript
/**
 * Validate file patterns in gate configuration.
 * Only validates types - glob syntax is validated at runtime via matching behavior.
 * This follows ecosystem patterns (Jest, ESLint, Webpack).
 *
 * @param gateConfig - Gate configuration to validate
 * @throws Error if any pattern is not a string
 */
export function validateFilePatterns(gateConfig: GateConfig): void {
  if (!gateConfig.file_patterns || gateConfig.file_patterns.length === 0) {
    return;
  }

  for (const pattern of gateConfig.file_patterns) {
    // Type validation - catches JSON parse errors, config mistakes
    if (typeof pattern !== 'string') {
      throw new Error(
        `Invalid file pattern in gate configuration: expected string, got ${typeof pattern}`
      );
    }

    // No syntax validation - minimatch is extremely lenient and will
    // attempt to interpret almost any string as a valid pattern.
    // Invalid patterns will simply not match any files at runtime.
  }
}
```

### Why This is Best

1. **Idiomatic:** Matches what Jest, ESLint, Webpack, and the broader ecosystem does
2. **Simple:** Minimal code, easy to understand and maintain
3. **Correct:** Catches actual errors (type mismatches) without false positives
4. **Philosophy-aligned:** Works with minimatch's lenient design, not against it
5. **User-friendly:** Users get natural feedback (pattern doesn't match → gate doesn't run → check pattern)

### What Needs to Change in the Plan

**Task 2.5 modification:**
1. Keep the try-catch structure
2. Change from `minimatch('', pattern)` test to `typeof pattern !== 'string'` check
3. Update error message to clarify it's type validation, not syntax validation
4. Add comment explaining the ecosystem rationale

**Revised implementation:**
```typescript
export function validateFilePatterns(gateConfig: GateConfig): void {
  if (!gateConfig.file_patterns || gateConfig.file_patterns.length === 0) {
    return;

  for (const pattern of gateConfig.file_patterns) {

    }
  }
}
```

This is significantly simpler and more maintainable than the original plan's approach.
