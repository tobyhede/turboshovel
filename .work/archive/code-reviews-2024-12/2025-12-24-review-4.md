## NON-BLOCKING (May Be Deferred)

**Inconsistent import style in cli.ts:**
- Description: The file uses both `import type` and `import` for the same module (schemas.ts). Line 3 uses `import type { HookInput }` while line 4 uses `import { parseHookInput }` separately. This works but is less idiomatic than combining them.
- Location: plugin/hooks/hooks-app/src/cli.ts:3-4
- Action: Consider combining imports: `import { parseHookInput, type HookInput } from './schemas';`

**Potential runtime issue with isNodeError type guard:**
- Description: The `isNodeError` type guard checks `'code' in error` but doesn't verify that `code` is actually a string property. Any Error with a `code` property (including custom errors with numeric codes or other types) will pass this check. While this matches NodeJS.ErrnoException in practice, it's technically not as precise as it could be.
- Location: plugin/hooks/hooks-app/src/errors.ts:4-6
- Action: Consider adding `typeof error.code === 'string'` check for stricter validation, or document why the simpler check is sufficient for the use case.

**Missing edge case test for parseHookInput:**
- Description: The schemas test suite doesn't verify behavior when JSON parses successfully but contains unexpected extra fields. While zod strips unknown fields by default, this is an important validation boundary behavior worth documenting through tests.
- Location: plugin/hooks/hooks-app/__tests__/schemas.test.ts
- Action: Add test case: `it('strips unknown fields', () => { const result = parseHookInput('{"hook_event_name":"PostToolUse","cwd":"/test","unknown":"field"}'); expect(result.data).not.toHaveProperty('unknown'); });`

**Empty input validation occurs before parseHookInput:**
- Description: In cli.ts lines 179-190, there's an explicit empty string check before calling `parseHookInput`. However, `parseHookInput` would also fail on empty string (JSON.parse("") throws). This creates redundant validation paths and different error messages for the same failure mode.
- Location: plugin/hooks/hooks-app/src/cli.ts:179-190
- Action: Either remove the early check and let parseHookInput handle it (simpler), or document why the early check provides better error messaging for this specific case.

**SESSION_STATE_KEYS includes optional field stashedWorkflowId:**
- Description: The `SESSION_STATE_KEYS` array includes `stashedWorkflowId` which is an optional field (marked with `?` in the interface). This is technically correct but worth noting that code using this array should handle optional fields appropriately when iterating.
- Location: plugin/hooks/hooks-app/src/types.ts:104-113
- Action: Add comment documenting that some keys are optional: `// Note: stashedWorkflowId is optional - check for undefined when iterating`
