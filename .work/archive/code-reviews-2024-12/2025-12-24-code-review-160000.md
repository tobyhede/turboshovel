While technically correct (it always returns the pessimistic variant), using `Conditions | null` would be more future-proof for when Task 5 adds support for `all: false`.
- Location: `/Users/tobyhede/psrc/turboshovel/plugin/hooks/hooks-app/src/workflow/parser/helpers.ts:167`
- Action: Consider changing return type to `Conditions | null`. This is deferred because Task 5 will need to update this function anyway.

**Tests could verify type narrowing behavior:**
- Description: The `Conditions discriminated union` tests verify that values can be created with both `all: true` and `all: false`, and include an exhaustive switch test. However, there's no test verifying that TypeScript correctly narrows the pass/fail semantics (e.g., that accessing `conditions.pass` after checking `conditions.all === true` gives the correct semantic interpretation). This is a documentation/clarity concern more than a correctness issue.
- Location: `/Users/tobyhede/psrc/turboshovel/plugin/hooks/hooks-app/__tests__/workflow/types.test.ts:162-193`
- Action: Consider adding a comment in the exhaustive switch test explaining the semantic difference between `true` (pessimistic) and `false` (optimistic) modes.

**Subtask.id could have stronger typing:**
- Description: `Subtask.id` is typed as `string` but according to the comment should only be `A-Z` letters or `{n}`. A union type like `string & { __brand: 'SubtaskId' }` or an enum/literal union could provide compile-time validation.
- Location: `/Users/tobyhede/psrc/turboshovel/plugin/hooks/hooks-app/src/workflow/types.ts:96`
- Action: Consider whether runtime validation in the parser is sufficient, or if a branded type (like `TaskNumber`) would add value. The current approach is pragmatic for this phase.
