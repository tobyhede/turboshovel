## BLOCKING (Must Address)

**Incorrect session.json path documentation:**
- Description: README claims session state is stored at `.claude/turboshovel/workflows/session.json` but implementation uses `.claude/turboshovel/session.json`
- Location: README.md:633 (Active Workflow Tracking section)
- Impact: Developers and agents looking for session state will search the wrong directory. This will cause confusion during debugging and workflow state inspection.
- Action: Change line 633 from "The active workflow ID is stored in `.claude/turboshovel/workflows/session.json`" to "The active workflow ID is stored in `.claude/turboshovel/session.json`"
- Evidence:
  - README.md:633: `.claude/turboshovel/workflows/session.json`
  - state.ts:7: `const SESSION_FILE = '.claude/turboshovel/session.json';`

**IF/ELSE conditionals documented but not implemented:**
- Description: README documents IF/ELSE conditional syntax (lines 507-520, 799-806, 909-914) but the parser has no implementation for IF or ELSE keywords
- Location: README.md:507-520, 799-806, 909-914
- Impact: Agents will write workflows using IF/ELSE syntax expecting it to work, but the parser will silently ignore these constructs (they'll be treated as implicit prompt text). This creates false expectations and broken workflows.
- Action: Either (1) Remove all IF/ELSE documentation until the feature is implemented, OR (2) Add clear "NOT YET IMPLEMENTED" warnings before each IF/ELSE example
- Evidence:
  - README shows IF/ELSE in multiple examples (lines 507-520, 587-590, 801-806, 909-914, 1012-1015)
  - parser.ts has no IF/ELSE handling code
  - helpers.ts parseConditional() only parses PASS/FAIL, not IF/ELSE
  - No tests exist for IF/ELSE parsing in __tests__/workflow/parser/

**BLOCKED condition documented but not implemented:**
- Description: README shows BLOCKED as a valid condition outcome (line 28, 570, 891) but it's not a recognized condition type in the parser
- Location: README.md:28, 570, 891 (execute.workflow.md example)
- Impact: Workflows using `- BLOCKED: STOP` will fail to parse or have undefined behavior. The parser only recognizes PASS and FAIL as condition types.
- Action: Either (1) Remove BLOCKED from condition examples and document it only as a task status (which it actually is), OR (2) Implement BLOCKED as a valid condition type in the parser
- Evidence:
  - README.md:28: `- BLOCKED: STOP "Agent reported BLOCKED. Escalate to user."`
  - parser/helpers.ts parseConditional() only handles 'PASS' and 'FAIL'
  - parser/types.ts ParsedConditional type is `'pass' | 'fail'` only
  - BLOCKED is only used as a task status in workflow/types.ts:78
