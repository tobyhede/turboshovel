## BLOCKING (Must Address)

### **Missing Commander dependency in package.json**
- **Description:** Task 3.1 uses `commander` package for CLI but Task 2.1 only adds `micromark`. The plan does not include installing `commander` dependency.
- **Location:** Phase 3, Task 3.1 (src/cli/workflow-cli.ts line 1730)
- **Impact:** Code will not compile or run - `import { Command } from 'commander'` will fail with module not found error
- **Action:** Add task between 2.1 and 3.1: "Install commander dependency" with `npm install commander` and commit

### **Missing @types/commander dev dependency**
- **Description:** TypeScript requires type definitions for commander package
- **Location:** Phase 3, Task 3.1
- **Impact:** TypeScript compilation will fail with type errors or force implicit any
- **Action:** Add `npm install -D @types/commander` to commander installation task

### **HookInput type mismatch - subagent_output vs output**
- **Description:** Task 4.4 (subagent-stop.ts) uses `input.subagent_output` but existing types.ts (line 14) defines field as `output?`. Plan code won't compile.
- **Location:** Task 4.4, line 2549 and 2569 (`input.subagent_output`)
- **Impact:** TypeScript compilation error - property does not exist on type HookInput
- **Action:** Change `input.subagent_output` to `input.output` in both test and implementation code

### **Inconsistent tool_input access pattern**
- **Description:** Task 4.3 (task-tracker.ts line 2479) uses `input.tool_input?.subagent_type` but HookInput type does not define tool_input field
- **Location:** Task 4.3, src/workflow/hooks/task-tracker.ts
- **Impact:** TypeScript error - tool_input not defined on HookInput interface
- **Action:** Verify if tool_input exists in actual runtime (may need to add to HookInput type) or document how to extract subagent type from Task tool calls

### **DispatchResult type conflict**
- **Description:** Dispatcher already defines DispatchResult interface (dispatcher.ts lines 34-38) but plan modifies it to add `continue` and `render` fields (Task 4.2 tests line 2287, 2288). Existing interface has different shape.
- **Location:** Task 4.2, __tests__/workflow/dispatcher-integration.test.ts
- **Impact:** Type mismatch - tests expect fields that don't exist on actual return type
- **Action:** Update test expectations to match actual DispatchResult shape (context, blockReason, stopMessage) not (continue, render)

### **Circular import risk - workflow module importing from dispatcher**
- **Description:** Plan creates workflow/context.ts which is imported by workflow/index.ts, but dispatcher.ts already imports from './workflow'. Adding `import { getWorkflowContext } from './workflow'` in dispatcher creates circular dependency risk.
- **Location:** Phase 4, Task 4.2 (dispatcher.ts modification)
- **Impact:** May cause module initialization issues or TypeScript compilation errors depending on bundler
- **Action:** Import directly from './workflow/context' instead of './workflow' to break cycle, OR structure exports carefully in workflow/index.ts

### **Missing test verification for file paths in Task 1.2**
- **Description:** Task 1.2 creates `.claude/turboshovel/workflows` directory (line 257) but test doesn't verify this matches STATE_DIR constant in implementation
- **Location:** Task 1.2, state.test.ts line 257 vs state.ts line 348
- **Impact:** Test could pass with wrong directory structure - brittle test
- **Action:** Extract STATE_DIR to shared constant or add test assertion that loaded state matches expected directory structure

### **Test relies on build artifacts**
- **Description:** Task 3.1 CLI test (line 1595) uses `dist/cli/workflow-cli.js` but plan doesn't ensure build happens before test
- **Location:** Task 3.1, __tests__/cli/workflow-cli.test.ts
- **Impact:** Tests will fail if dist/ doesn't exist or is stale
- **Action:** Add build step to test setup OR change test approach to use ts-node/tsx for TypeScript execution

### **Missing validation for GOTO self-loop**
- **Description:** Parser validation (line 1504) logs warning for GOTO self but doesn't block - allows infinite loop possibility
- **Location:** Task 2.3, src/workflow/parser/parser.ts line 1504
- **Impact:** Workflow execution could hang indefinitely if step has GOTO to itself
- **Action:** Either make this a hard error (throw WorkflowSyntaxError) or document as intentional feature with escape mechanism

### **No error handling for workflow file not found in CLI**
- **Description:** workflow start command (line 1757-1759) reads file but only catches generic Error - doesn't distinguish file not found from parse errors
- **Location:** Task 3.1, src/cli/workflow-cli.ts
- **Impact:** Poor user experience - "Error: undefined" instead of clear "File not found" message
- **Action:** Add specific error handling for ENOENT with helpful message suggesting file path resolution

### **Session file location conflict**
- **Description:** Workflow state manager uses `.claude/.session.json` (line 349) but existing session.ts uses different session mechanism. Risk of conflicts or confusion.
- **Location:** Task 1.2, src/workflow/state.ts line 349
- **Impact:** May overwrite existing session data or cause confusion about which session system is authoritative
- **Action:** Use `.claude/turboshovel/session.json` or extend existing Session class instead of creating parallel session file

## Assessment

**Conclusion:**

The plan is comprehensive and well-structured with good TDD discipline, but contains critical blocking issues that will prevent compilation and execution:

1. Missing dependencies (commander, @types/commander)
2. Type mismatches between plan code and existing codebase (HookInput fields)
3. Architectural conflicts (DispatchResult interface, session file location)
4. Missing error handling in critical paths

The plan demonstrates strong understanding of the codebase architecture and follows existing patterns well. The test-first approach is correctly applied throughout. However, it appears to have been written without verifying field names against the actual HookInput type definition, leading to several type errors.

**Confidence in findings:**

HIGH - Verified against actual codebase files (dispatcher.ts, types.ts, package.json)
- All blocking issues confirmed by reading source files
- Type mismatches verified against line-by-line comparison
- Dependency issues confirmed by checking package.json

MEDIUM - Workflow execution behavior
- Cannot fully verify runtime behavior without execution
- Some issues (task completion order, GOTO loops) require runtime testing

The blocking issues must be fixed before implementation begins. The suggestions would improve quality but are not mandatory for initial implementation.
