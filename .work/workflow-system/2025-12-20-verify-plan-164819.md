## BLOCKING (Must Address)

**Missing dependency: commander package**:
- Description: Plan requires `commander` package for CLI implementation (Task 3.1) but it is not installed in the project. The plan includes CLI tests and implementation that depend on this package.
- Location: Task 2.1 adds micromark, Task 3.1 uses commander without installation
- Impact: CLI implementation will fail with "Cannot find module 'commander'" error. Build and tests will fail.
- Action: Add Task 2.1b between Tasks 2.1 and 2.2 to install commander: `cd plugin/hooks/hooks-app && npm install commander` with appropriate commit.

**Missing HookInput fields required by workflow hooks**:
- Description: Plan's workflow hooks use `input.tool_input` and `input.subagent_output` fields that don't exist in the current HookInput type definition
- Location: Task 4.3 (task-tracker.ts line 2479), Task 4.4 (subagent-stop.ts line 2549, 2569, 2655)
- Impact: TypeScript compilation will fail with "Property does not exist" errors. Tests will not match actual hook input structure.
- Action: Either (1) Update types.ts to add these fields to HookInput interface before implementing workflow hooks, OR (2) Update workflow hook implementations to use existing fields (tool_name, output instead of subagent_output)

**Incorrect HookInput field name**:
- Description: Plan uses `input.user_message` but actual HookInput type defines `user_message` not `user_prompt`
- Location: Task 4.2 references `user_prompt: 'test prompt'` (line 2282) but should use `user_message`
- Impact: Test will fail due to incorrect field name
- Action: Change line 2282 from `user_prompt: 'test prompt'` to `user_message: 'test prompt'`

**Inconsistent GateResult vs DispatchResult return types**:
- Description: dispatcher.ts returns DispatchResult with `context`, `blockReason`, `stopMessage` fields. Plan's Task 4.2 test expects `continue` and `render` fields which don't exist in DispatchResult.
- Location: Task 4.2, lines 2287-2289, 2301-2303
- Impact: Tests will fail - DispatchResult doesn't have `continue` or `render` fields
- Action: Update test expectations to match actual DispatchResult interface: check for `context` field containing workflow context, remove checks for `continue` and `render`

**Session file path incorrect**:
- Description: Plan's state manager uses `.claude/.session.json` but this conflicts with potential Claude Code internal files. Better to use turboshovel-specific path.
- Location: Task 1.2, line 349
- Impact: May conflict with Claude Code's own session management or other plugins
- Action: Change SESSION_FILE constant to `.claude/turboshovel/.session.json` to namespace properly

**Test path pattern mismatch**:
- Description: Plan uses `--testPathPattern="workflow/types"` but Jest expects patterns to match full paths. Current tests use patterns like `config.test` or file paths.
- Location: All test run commands throughout the plan (e.g., lines 82, 194, 336, etc.)
- Impact: Tests may not run or may run unintended tests
- Action: Change test patterns from `"workflow/types"` to `"workflow/types.test"` to match filename convention

**Missing test directory creation**:
- Description: Tests create temporary directories but the actual .claude/turboshovel/workflows directory structure may need recursive creation in state manager
- Location: Task 1.2, state.ts save() method line 408
- Impact: Directory creation with `{ recursive: true }` is correct, but pattern should match test expectations
- Action: Verify that stateDir path in test (line 257) matches actual implementation path. Test expects `.claude/turboshovel/workflows`, implementation uses same - this is correct.

**Invalid action type in formatAction helper**:
- Description: formatAction function (Task 3.1, line 1976) uses complex conditional type that references Step['conditions'] which may not infer correctly
- Location: Task 3.1, lines 1976-1986
- Impact: TypeScript compilation error - overly complex type inference
- Action: Simplify type to: `function formatAction(action: Action): string` since Action is already a discriminated union

**Parser implementation doesn't use micromark**:
- Description: Task 2.3 comment states "Uses micromark for tokenization" but implementation uses regex-based line-by-line parsing, not micromark AST
- Location: Task 2.3, lines 1275-1289
- Impact: Misleading documentation, micromark dependency is unused deadweight
- Action: Either (1) Remove micromark dependency and update comment to say "regex-based parser", OR (2) Actually implement micromark-based parsing

**Missing validation for H1 rejection**:
- Description: Test expects H1 headers to be rejected (line 1237) but parser only checks for `##` prefix without explicitly rejecting `#` (single hash)
- Location: Task 2.3, parser.ts lines 1300-1320 and test line 1228-1238
- Impact: Parser may not reject H1 headers as intended
