## RECOMMENDATIONS

### 1. Library Recommendation: mdast-util-from-markdown + micromark

**Rationale:** This combination provides:
- Direct architectural equivalence to pulldown-cmark (tokenizer + AST builder)
- Full TypeScript support
- Extensibility for custom syntax if needed
- CommonMark compliance matching pulldown-cmark

**Alternative:** markdown-it for simpler implementation with less ecosystem overhead

**NOT recommended:** Hand-rolling the parser (unnecessary since markdown structure is standard)

### 2. Complete TypeScript Type Definitions

```typescript
// Branded type for step numbers (1-indexed, never zero)
declare const __brand: unique symbol;
type Branded<T, B> = T & { [__brand]: B };
type StepNumber = Branded<number, 'StepNumber'>;

// Smart constructor
function createStepNumber(n: number): StepNumber | null {
  return n > 0 ? (n as StepNumber) : null;
}

// Discriminated union for actions
type Action =
  | { readonly type: 'CONTINUE' }
  | { readonly type: 'STOP'; readonly message?: string }
  | { readonly type: 'GOTO'; readonly step: StepNumber };

// Conditions (atomic - both branches always present)
interface Conditions {
  readonly pass: Action;
  readonly fail: Action;
}

// Command with code content
interface Command {
  readonly code: string;
}

// Prompt with text content
interface Prompt {
  readonly text: string;
}

// Step - the main workflow unit
interface Step {
  readonly number: StepNumber;
  readonly description: string;
  readonly command?: Command;
  readonly prompts: readonly Prompt[];
  readonly conditions?: Conditions;
}

// Parse result type
type ParseResult<T> =
  | { readonly success: true; readonly value: T }
  | { readonly success: false; readonly error: ParseError };

interface ParseError {
  readonly message: string;
  readonly line?: number;
  readonly column?: number;
}

// Main parser function signature
function parseWorkflow(markdown: string): ParseResult<readonly Step[]>;
```

### 3. Recommended Parsing Strategy: Option C (Hybrid)

**Approach:**
1. Use `mdast-util-from-markdown` to parse markdown into standard mdast AST
2. Walk the AST to extract workflow-specific semantics
3. Transform to workflow Step[] structure

**Implementation Sketch:**
```typescript
import { fromMarkdown } from 'mdast-util-from-markdown';
import type { Root, Heading, Code, Paragraph, Strong, Text } from 'mdast';

function parseWorkflow(markdown: string): ParseResult<readonly Step[]> {
  const tree = fromMarkdown(markdown);
  const steps: Step[] = [];
  let currentStep: Partial<Step> | null = null;
  let pendingConditionals: { pass?: Action; fail?: Action } = {};

  for (const node of tree.children) {
    if (node.type === 'heading' && node.depth === 2) {
      // Finalize previous step
      if (currentStep) {
        steps.push(finalizeStep(currentStep, pendingConditionals));
        pendingConditionals = {};
      }
      // Parse step header
      currentStep = parseStepHeader(node);
    } else if (node.type === 'code' && currentStep) {
      // Handle code block
      if (node.lang === 'bash') {
        if (currentStep.command) {
          return { success: false, error: { message: 'Multiple code blocks per step not allowed' } };
        }
        currentStep.command = { code: node.value.trim() };
      }
    } else if (node.type === 'paragraph' && currentStep) {
      // Check for conditionals, prompts, or implicit text
      parseConditionalOrPrompt(node, currentStep, pendingConditionals);
    }
    // ... handle lists for list-based conditionals
  }

  // Finalize last step
  if (currentStep) {
    steps.push(finalizeStep(currentStep, pendingConditionals));
  }

  // Validate
  return validateWorkflow(steps);
}
```

### 4. Error Handling Recommendation: Custom ParseResult Type

**Rationale:**
- Simpler than adding `neverthrow` dependency
- Matches Zod's `safeParse` pattern already familiar in TypeScript ecosystem
- Allows detailed error messages with location information
- No try/catch needed in calling code

```typescript
type ParseResult<T> =
  | { readonly success: true; readonly value: T }
  | { readonly success: false; readonly error: ParseError };
```

## QUESTIONS (Unresolved or for further investigation)

- **Micromark Extension Complexity:** Creating custom micromark extensions for workflow-specific syntax (conditionals) may be overkill. The hybrid approach (standard mdast + custom walker) should suffice for current syntax.
- **Performance Requirements:** The Rust implementation is designed for interactive CLI use. TypeScript performance should be adequate, but if parsing large workflows becomes a concern, pulldown-cmark-wasm could be considered.
- **Streaming vs. Full Parse:** Rust uses pull-parsing which is memory-efficient. For TypeScript, full AST construction should be fine given typical workflow sizes.

## Risk Assessment

### High Risk: Separator Permissiveness
The Rust parser is very permissive with separators. The TypeScript implementation must exactly match the `strip_separator` function behavior to avoid subtle parsing differences.

**Mitigation:** Port the Rust tests for header and conditional parsing first.

### Medium Risk: Implicit Prompt Detection
Implicit prompts (text that becomes a prompt when no code block exists) have complex rules about when to capture text vs. ignore it.

**Mitigation:** Study Task 2.4 tests in parser.rs carefully; implement comprehensive test coverage.

### Low Risk: Backward Compatibility Syntax
The parser supports both ALLCAPS (new) and legacy (Pass:/Fail:, Go to Step N) syntax. This must be preserved.

**Mitigation:** Port legacy syntax tests explicitly.

## Assessment

**Conclusion:**
The recommended approach is:
1. **Library:** `mdast-util-from-markdown` (or simpler `markdown-it`)
2. **Strategy:** Hybrid - standard markdown parsing + custom AST walker
3. **Types:** Discriminated unions with branded StepNumber
4. **Errors:** Custom ParseResult type (Zod-style)
5. **Testing:** Port all 50+ Rust tests first, then add examples as fixtures

**Implementation Effort Estimate:**
- Type definitions: 1-2 hours
- Core parser with mdast walker: 4-6 hours
- Test porting: 2-3 hours
- Edge case handling and refinement: 2-4 hours
- **Total:** 10-15 hours for feature parity

**Confidence in findings:**
HIGH for library selection and type design. MEDIUM for exact implementation details of implicit prompt handling and separator parsing - these will need careful test-driven development.
